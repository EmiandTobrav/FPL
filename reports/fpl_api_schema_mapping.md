# FPL API Schema Mapping Audit

## Scope

This audit maps the current Vaastav-style `merged_gw` columns to official Fantasy Premier League API fields. It does not change the modelling pipeline or model code.

Sources inspected locally:

- `data/interim/all_merged_gw.parquet`: (246496, 75)
- `data/processed/modeling_dataset.parquet`: (105866, 123)
- `src/data/download_vaastav.py`
- `src/features/rolling_features.py`
- `src/features/target_builder.py`
- `src/data/build_dataset.py`
- `src/features/team_strength.py`
- `src/models/baseline.py`

Official API endpoints sampled:

- https://fantasy.premierleague.com/api/bootstrap-static/
- https://fantasy.premierleague.com/api/fixtures/
- https://fantasy.premierleague.com/api/event/{gw}/live/
- https://fantasy.premierleague.com/api/element-summary/{player_id}/

## Answer

Yes, the official FPL API can recreate enough Vaastav-style `merged_gw` rows for the current pipeline for the current season and future seasons, with one important constraint: the official API is current-season oriented. Historical multi-season backfills still need archived data or saved API snapshots.

The essential current pipeline columns are covered. Missing columns are mostly older granular Opta-style fields that are passed through but not used by the current feature, target, team-strength, baseline, or model code.

Essential columns unavailable from the sampled official endpoints: 0.

## Current Pipeline Needs

The current build requires a player key, `season`, `gw`, `total_points`, and `minutes`. Rolling features also require `bonus` and `bps`. Position filtering uses `position`. Team-strength features need `team`, `opponent_team`, `was_home`, `fixture`, `team_h_score`, and `team_a_score`. Optional candidate features use goals/assists/clean sheets/goals conceded, ICT, expected stats, selected, transfers, and value.

Stable model features are generated by the pipeline; they do not require raw `team` or `opponent_team` as model inputs.

## Missing Columns That Matter

None.

No unavailable column is essential to the current pipeline. If future experiments want pass, chance, or manager-specific features such as `attempted_passes`, `key_passes`, `big_chances_created`, or `mng_win`, those would require another source or must be dropped from the Vaastav-style recreation.

## Endpoint Responsibilities

- `bootstrap-static`: player metadata (`id`, names, `element_type`, `team`, `now_cost`) plus team and position lookup tables.
- `element-summary/{player_id}`: closest replacement for Vaastav `merged_gw`; `history` contains one row per player fixture with `round`, `fixture`, `opponent_team`, `was_home`, points, minutes, BPS, bonus, expected stats, ownership, transfers, and historical value.
- `fixtures`: fixture metadata and scores by fixture id; useful to validate or fill `team_h_score`, `team_a_score`, `team_h`, `team_a`, kickoff time, and fixture event/GW.
- `event/{gw}/live`: gameweek live stats by player. Useful for current/recent GW ingestion and validation, but less convenient than `element-summary` for all historical player fixture rows because fixture-level details are nested in `explain`.

## Recommended Implementation Plan

1. Build an FPL API ingestion module separate from `download_vaastav.py`.
2. Fetch `bootstrap-static` once per run and create lookup tables for players, teams, and positions.
3. Fetch `fixtures` once per run and index by fixture id.
4. For each active player id from bootstrap, fetch `element-summary/{player_id}` and normalize each `history` row to the Vaastav-style schema.
5. Add `season` from configuration, set `gw = history.round`, and keep `GW` as an alias if compatibility is needed.
6. Join player metadata from bootstrap: `name`, `position`, and `team`.
7. Prefer `history.value` for historical row price; use `bootstrap.elements.now_cost` only for current snapshot/future rows.
8. Fill unavailable, unused Vaastav columns with missing values only if downstream schema compatibility requires them.
9. Run the existing `build_modeling_dataset` on the recreated frame and compare row counts, required-column coverage, duplicate player-season-GW behavior, team-strength diagnostics, and model-feature availability against the Vaastav interim parquet.
10. Add tests for one synthetic bootstrap player, fixture row, and element-summary history row to prove the mapper emits the required Vaastav-style columns without adding raw team/opponent fields to model features.

## Caveats

- Official API field availability can change between FPL seasons. The ingestion code should validate required fields at runtime and write a schema diagnostics report.
- `selected`, transfers, and `value` are available in `element-summary.history`, but their exact timing should still be treated conservatively; the current pipeline uses ownership/transfers only as lagged features.
- Historical seasons before the current API season are not available from these endpoints unless separately archived.
